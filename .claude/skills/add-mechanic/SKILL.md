# Добавление механики: $ARGUMENTS

Источник правды — `docs/architecture.md` (раздел «Добавление механики»). Перед началом прочитать его и профильный документ: `chain-budget.md`, `damage-effects.md`, `devices.md` или `levels/*.md`.

## 0. Уточнить границы

- Сформулировать, где действует механика: стартовое состояние, развитие боя или правила конкретного режима (обучение, лес, поход, замок, редактор). Не распространять её на другие режимы без основания.
- Сформулировать критерии приёмки через наблюдаемый игроком результат, а не через таблицы реализации.
- Если трактовка неоднозначна и от неё зависит архитектура — спросить пользователя.

## 1. Карта изменений

| Слой | Файл | Что проверить |
|---|---|---|
| Данные | `components.ts`, `forestTypes.ts` | Компонент на `ForestCell` или отдельное поле состояния (как `state.devices`, `state.pits`) |
| Прямой урон, HP, смерть | `combatRules.ts`, `cellLife.ts` | Источник урона (`physical`/`item`/`hazard`/`effect`); жизнь только через `cellLife`, не `hp > 0` |
| Накопленные эффекты | `damageEffects.ts` + `effectRules.ts` | Чистые переходы отдельно от привязки к сущностям |
| Ответ врагов | `enemyPhase.ts` | Общий выбор атакующих для прогноза и исполнения |
| Порядок хода | `turnSystems.ts` | Событие публикуется, когда состояние уже соответствует ему; без скрытых доп. ходов и повторной обработки крупных фигур |
| Ожидание, отмена | `turnRuntime.ts` | Проверка поколения сцены после каждого ожидания |
| Прогноз | `forestSystems.ts` | Считается на копии поля, без RNG и событий; раздельные поля урона |
| Генерация | `boardGeneration.ts`, `forestEngine.ts` | Новые клетки исключены из пополнения, если это нужно; выжившие не перекрашиваются |
| Бои карты | `run/battles/*.ts`, `lessonBuilder.ts`, `run/forestMap.ts` | Инструменты открывает поход (`grants`, находки), движок проверяет `runNode.allowed*` |
| Редактор, JSON | `customLevel.ts`, `editor/LevelEditor.ts` | Валидация, обратная совместимость старого JSON, UI выбора |
| Рендер, звук | `render/*.ts`, `audio.ts` | Реагируют на события и не влияют на результат; многоклеточные фигуры через `uniqueEntities` |
| Арт | `characterAssets.ts` | Новый `kind`/`variant` → `CHARACTER_ART_IDS`, процедурный резерв (скилл `character-art`) |

Новый тип врага требует согласовать все слои: универсального реестра поведений нет.

## 2. Тесты

- Логический набор `src/game/<механика>.spec.ts`, скрипт `test:<механика>` в `package.json`.
- Покрыть: прогноз совпадает с исполнением; промежуточное состояние на событиях; порядок фаз; отмена из обработчика; смерть кота раньше победы; replay по seed.
- При изменениях UI — Playwright-сценарий в `tests/` и добавление его имени в `testMatch` в `playwright.config.ts`.

## 3. Документация (в той же задаче)

- `README.md`: правила, управление, список проверок.
- `docs/architecture.md`: модуль, фаза хода.
- Профильный документ или новый в `docs/`; для боёв карты — `docs/levels/` и `docs/biomes/forest-map.md`.
- Удалить устаревшие утверждения. Результаты проверок датировать.

## 4. Приёмка

Скиллы `verify-all` (с `--browser`, если затронут UI), `determinism-check`, затем `docs-sync`. Сверить результат с исходной формулировкой запроса.
