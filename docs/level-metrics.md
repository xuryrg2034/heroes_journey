# Метрики уровней: анализатор

Анализатор уровня автоматически оценивает авторские бои карты леса и уровни редактора: насколько поле «переплетено», сложен ли бой, требует ли он изучаемой механики и сколько в исходе удачи. Код — `src/game/levelAnalysis.ts` (чистая логика, пригодна для редактора), CLI — `scripts/analyze-levels.ts`, тест — `src/game/levelAnalysis.spec.ts` (`npm run test:level-analysis`). Целевые диапазоны для разных типов боёв — в [руководстве по дизайну боёв](level-design-guide.md), раздел 9; здесь только определения.

**Все значения — оценочные эвристики, не доказательство.** Поиск ограничен глубиной, шириной луча и бюджетом узлов; агенты — выборкой прогонов. Флаги `exhaustive`, `budgetExhausted`, `unresolvedFirstActions` и доверительные интервалы показывают, насколько результату можно верить.

## Запуск

```sh
npm run analyze:levels                                      # все бои реестра карты (как --nodes)
npm run analyze:levels -- --node chief-breakfast --depth 4  # один бой реестра или узел карты, глубже
npm run analyze:levels -- --node wolf-ford --row 5          # бой реестра на другом ряду карты
npm run analyze:levels -- --node den-nest --energy 5         # вход с энергией из прошлых узлов
npm run analyze:levels -- --nodes --talismans all           # с талисманами похода (по умолчанию — без них)
npm run analyze:levels -- --node troll-lair --ladder 4       # на ступени «Ступеней клятвы» (по умолчанию 0)
npm run analyze:levels -- --json my-level.json --out report.json
```

Консоль печатает три таблицы (структура и поиск; агенты и информация; цели и выход) и время. Третья таблица: `goalT`, `exitT`, `hpExit` — ходы до целей, ходы до выхода и HP при выходе у оракула (seed 0, в пределах горизонта); для случайного (R) и жадного (G1) агентов — доля прогонов с целями (`goal%`), доля побед (`win%`), медианы ходов до целей (`goalT`), до выхода (`exitT`), задержки (`delay` = exitT − goalT) и HP при выходе (`hp`); `G1 stuck` — прогоны жадного, выполнившие цели без выхода. JSON содержит `meta` (дата, параметры, время по боям) и `levels[]` с полями, описанными ниже. Вне `meta` отчёт детерминирован: одинаковый уровень и параметры дают одинаковый JSON.

## Как считается

**Изоляция.** Анализ читает позицию только через `ForestEngine.captureAnalysisSnapshot()` (глубокая копия состояния, RNG, аллокатора ID и служебных полей) и работает на собственных экземплярах движка через `restoreAnalysisSnapshot()`. Живая игра не меняется, её RNG не сдвигается. Каждое действие выполняется обычными командами движка (`releaseChain`, `useAbility`, `waitTurn`, `useItem`) при `animationScale = 0`, а прогноз берётся из `preview`/`previewAbility`/`previewItem` — те же функции, что у игрока. Разрешения инструментов боя узла (`allowedItems`, `allowedAbilities` похода) проверяет движок.

**Действие игрока** — одно из:
- обычная цепь из `availableMoves(16)` (движок уже дедуплицирует пути по исходу и ограничивает список 240 путями и 1700 проверками на старт);
- прыжок на каждую клетку, где `previewAbility('jump')` допустим; круговой удар; отдых;
- предмет на цель (не тратит ход, затем действие того же хода). Бомба на врага с 0 HP отбрасывается как шум; в каждом узле, включая корень, остаются `itemBeam = 3` лучших по оценке предмета — это эвристическое усечение (`stats.itemCuts`).

Различимые действия — действия с разным итоговым состоянием: дети корня дедуплицируются по хэшу значимого состояния (всё `ForestState`, кроме текстов, очков и статических данных уровня, плюс RNG и `nextId`).

**Seed пополнения.** Seed 0 — настоящий поток RNG уровня. Остальные получаются подменой состояния RNG в снимке стартовой позиции (`variantSeed`). Поэтому стартовая расстановка, включая случайно заполненные при загрузке клетки авторского JSON, одинакова для всех seed; меняется только последующее пополнение. Это отличается от «копии определения с другим seed», которая перегенерировала бы и незакрашенные стартовые клетки.

## B. Оракул O: поиск по дереву ходов (`search[]`, по одному на seed)

Поиск знает настоящий seed и, следовательно, будущие пополнения. Поэтому он называется **оракулом (O)**: игрок этого знания не имеет (см. планировщик S ниже).

Алгоритм: итеративное углубление по ходам 1…`depth`. Корень — полная ширина. Во внутренних узлах действия упорядочены по оценке прогноза: 10 × прогресс по целям боя (снятые HP и убийства целей, включая смерти в фазе врагов из `enemyPhase.deaths` — таран, шипы, колючки, провал, стрела, дубина) + 2 × убийства + снятые HP + энергия − 8 × входящий урон − 30, если кот останется с 1 HP или меньше; победа первой, смерть последней. Раскрываются все побеждающие плюс `beam` лучших. (До 30 сентября 2026 штраф был 40 за каждую единицу урона, и луч отсекал ходы, платящие HP за прогресс.) **Победа** действия — `completesRoom` (бой кончается в цепи) или `enemyPhase.completesObjective` (движок прогнозирует победу в фазе врагов: цели выполнены с учётом засчитанных смертей и завершённого хода). На последнем ходу горизонта исполняются победы, отдых (его фаза врагов тоже может выиграть, а прогноза отдыха нет), предметы и действия, после которых по правилу тика движка (`tickDamageEffects`) горение или яд на прогнозном HP добьют цель боя (отмеченную цель, босса для `bossKills`, любого врага для `kills`) — с 01.10.2026 прогноз (тот же ход на копии мира) сам учитывает гибель врагов от их тиков в `enemyPhase.completesObjective` для цепей, отдыха и способностей, поэтому такие ходы становятся победными; эвристика `tickMayWin` остаётся для предметов и частично дублирует прогноз (`stats.lateWinChecks`). Для авторских уровней с прямой целью «выжить N ходов» исполняются все действия. **Бой с дверью** (завершение `exit`; с 02.10.2026 — все бои карты): цели только открывают дверь, победа — вход в открытую дверь цепью (`opensDoor`, `completesRoom`). Фаза врагов такой бой не выигрывает, поэтому в нём отдых и тики не считаются «поздней победой» на последнем ходу горизонта. Дверь не цель: до целей она закрыта (`planChain` отклоняет цепь в неё) и в оценке не участвует; после целей прогресс по целям равен 0, а вместо него оценка получает 10 × приближение к двери — на сколько шагов цепи (соседство цепи, по проходимым клеткам, без учёта занятости) клетка кота после действия и фазы врагов ближе к ближайшей двери, чем до него. (До 02.10.2026 дверь имела вес цели 1 и до целей — фактически без действия, потому что закрытая дверь в цепь не входит, — а после целей у луча и жадного агента не было стремления к ней.) Ходы до целей считаются отдельно: узел, где цели выполнены (`customLevel.goalCompletedTurn` задан или победа) и кот жив, — 0 ходов до целей; на последнем ходу горизонта действие, которое по прогнозу выполняет цели (`unlocksExit` цепи или фазы врагов) или побеждает, даёт 1 ход без исполнения. Результат узла хранится по ключу «хэш состояния с RNG + остаток глубины». Бюджет — число новых вычислений списка действий (`nodeBudget`); кэш списков общий для всех поисков одного боя (списки не зависят от RNG). Ход, выигранный с полным HP, дальше не углубляется: улучшить его нельзя.

| Поле | Определение |
| --- | --- |
| `winnable` | Найдена победа в пределах `depth` (в бою с дверью — вход в дверь) |
| `minTurns` | Минимум ходов (приращение `state.turn`) до `WIN`; предмет ход не тратит. В бою с дверью — **ходы до выхода** |
| `minGoalTurns` | Минимум ходов до выполнения целей с живым котом, найденный в пределах `depth` (в бою с дверью — открытие двери); `null` — не найдено. В бою без двери совпадает с `minTurns`. Луч и бюджет усечены, поэтому это верхняя оценка истинного минимума |
| `bestHp`, `bestHpAtMin` | Максимальное HP кота при любой найденной победе; при победе за `minTurns` (в бою с дверью — **HP при выходе**) |
| `firstActions` | Число различимых первых действий |
| `solutionsAtMin` | Различимые первые действия, ведущие к победе за `minTurns` |
| `firstMoveWinShare` | Доля первых действий, после которых победа найдена в пределах горизонта |

| `unresolvedFirstActions` | Первые действия без победы, которые бюджет не дал проверить до конца (не входят ни в долю побед, ни в ловушки) |
| `solutionLine`, `lineShares` | Одна оптимальная линия (максимум HP, затем порядок движка) и **wₜ** — доля различимых действий в позиции t, сохраняющих оптимум. w₀ = `solutionsAtMin / firstActions`; глубже — полной шириной |

## Честный планировщик S и зависимость от удачи (`planner`)

По Isaksen et al. 2017 поиск с настоящим seed «подглядывает» будущее пополнение. Планировщик S не знает seed:

1. Кандидаты: все победы этого хода (в цепи или в фазе врагов) и `plannerCandidates` = M первых ходов после **отбора**: каждый несмертельный первый ход проверяется оракулом на одном дополнительном пересэмплированном пополнении (не на оценочных seed, со своим бюджетом); сначала выигравшие там, затем неразрешённые, при равенстве — порядок прогноза. Раньше кандидатами были M лучших по оценке прогноза, и ложный FG > 0 появлялся, когда устойчивый ход не попадал в верх оценки (бои `boar-garden`, `den-nest`, 30.09.2026).
2. Для кандидата A **устойчивость** r(A) = доля побед среди разрешённых пересэмплирований из K = `plannerResamples`: после A оракул находит победу за оставшиеся `depth − 1` хода. У каждого кандидата свой бюджет `nodeBudget`; пересэмплирование, которое бюджет не разрешил, не считается поражением (`candidates[].unresolved`), а при нуле разрешённых r = `null`. Победа этого хода наступает до пополнения: r = 1 без пересэмплирования.
3. S выбирает argmax r среди разрешённых (при равенстве — лучший прогноз) и играет его на всех оценочных seed.

| Поле | Формула |
| --- | --- |
| `pOracle`, `oracleUnresolved` | P(O) = доля побед оракула среди **разрешённых** оценочных seed |
| `pHonest`, `honestUnresolved` | P(S) = доля побед после выбранного S первого хода среди разрешённых оценочных seed. Исход берётся из результата оракула для этого первого хода, а если он не разрешён — из отдельного поиска со свежим бюджетом |
| `fortuneGap`, `fortuneGapSeeds` | **FG = среднее (O(seed) − S(seed))** по seed, разрешённым и для O, и для S (парная разность; при полном разрешении равна P(O) − P(S)): какая часть проходимости держится на знании пополнения; `null`, если таких seed нет |

**Разрешённость — одно правило для O и S** на каждом оценочном seed: найденная победа — победа (даже если бюджет кончился позже); «победы нет» засчитывается, только если поиск уложился в бюджет (у оракула — нет `unresolvedFirstActions`, у S — `complete`); иначе seed не разрешён и не входит ни в числитель, ни в знаменатель, а учитывается в `*Unresolved`. До 30.09.2026 P(O) считал неразрешённый seed проигрышем, а P(S) его исключал, и при `budgetExhausted` FG мог занижаться и уходить в минус.
| `candidates`, `choice` | r(A) по кандидатам; выбранный ход |
| `robustFirstMoves` | Число кандидатов с r ≥ 0,8 (упрощённая проверка первого хода) |

Упрощение: скрыто только пополнение после первого хода; дальше S снова играет оракулом. FG поэтому — нижняя оценка зависимости от удачи. До 30 сентября 2026 все кандидаты делили один бюджет, и неразрешённые поздние кандидаты считались проигрышными: это давало ложный FG > 0 (например, FG = 1 у боя `boar-garden`).

## C. Ограниченные решатели и необходимость механики (`restricted`)

Методика «урезанного агента» (Green et al. 2018): тот же поиск на seed 0 с отключением X ∈ {`abilities`, `items`, `devices` — цепь не проходит клетки устройств, `prisms` — цепь не проходит кристаллы}. `applicable: false`, если X в бою нет (способности не разрешены, нет предметов в запасе, нет устройств, нет кристаллов и они не могут появиться).

| Поле | Определение |
| --- | --- |
| `winnable`, `minTurns`, `bestHp`, `exhaustive` | Результат поиска без X |
| `requires` | Оракул с X нашёл победу, без X — нет (в пределах горизонта; при `exhaustive: false` это указание, не доказательство) |
| `benefitTurns`, `benefitHp` | `minTurns(без X) − minTurns(с X)`; `bestHp(с X) − bestHp(без X)` |
| `agents` | Агенты без X |
| `needRandom`, `needGreedy` | **N_X = I(агент без X) − I(агент с X)** в битах. Если без X побед нет, `bits = null`, `atLeast` — нижняя граница по Уилсону. У случайного агента N_X структурно смещён вниз: без X у него меньше вариантов, и доля хороших цепей среди оставшихся может вырасти, поэтому N_X < 0 не означает «инструмент мешает». Для необходимости опирайтесь на `requires`/`benefit*` поиска и на N_X жадного агента |

## D. Агенты (`agents`) и информация решения

- **R, случайный агент:** равномерно выбирает среди всех действий узла (включая предметы). `agentRuns` прогонов на seed.
- **G1, жадный агент:** по немедленному результату прогноза — победа сейчас (в цепи или прогнозируемая в фазе врагов; в бою с дверью — вход в дверь) > выживание > (бой с дверью после целей) ближе к двери после действия > убийства (включая смерти врагов в фазе врагов) > снятые HP > безопасный конец > меньший входящий урон; предметы не использует. До целей дверь закрыта и агента не притягивает: он остаётся «самой сильной цепью». Детерминирован, поэтому один прогон на seed: при 3 seed P(G1) ∈ {0, 1/3, 2/3, 1}. (До 02.10.2026 критерия двери не было: после целей жадный агент продолжал брать самую сильную цепь и выходил, только если вход в дверь оказывался среди его ходов.)
- Победа агента — фаза `WIN`, то есть в бою с дверью только вход в неё; выполнение целей отмечается отдельно (ход и HP кота).
- Лимит — `agentTurnLimit` ходов (12).

| Поле | Определение |
| --- | --- |
| `winRate`, `winRateCi95` | P̂ = побед / прогонов; 95% интервал Уилсона: (p̂ + z²/2n ± z·√(p̂(1−p̂)/n + z²/4n²)) / (1 + z²/n), z = 1,96 |
| `info` | **I = −log₂ P̂** бит (Shen & Sturtevant 2024, «информация решения»). При P̂ = 0 `bits = null` (бесконечность), `atLeast = −log₂(верхняя граница Уилсона)` |
| `winHpMedian`, `winHpP10` | Медиана и 10-й перцентиль HP кота в победных прогонах — запас прочности |
| `avgHp`, `avgTurns`, `avgWinTurns`, `losses` | Средние; поражения до лимита |
| `goals`, `goalRate` | Прогоны, выполнившие цели с живым котом (в бою с дверью — открывшие её), и их доля |
| `goalTurnsMedian`, `winTurnsMedian` | Медиана ходов до целей (по прогонам с целями) и до победы (по победам; в бою с дверью — **ходы до выхода**) |
| `exitDelayMedian`, `hpLostAfterGoalMedian` | По победам: медиана ходов от целей до выхода (0 — цепь, выполнившая цели, вошла в дверь) и HP, потерянных за это время |
| `goalsNoExit` | Прогоны, выполнившие цели, но не вышедшие: кот погиб или кончился лимит ходов |

Высокое P(R) — бой решается почти любыми действиями. Высокое P(G1) — бой решается очевидной «самой сильной цепью».

## Обманчивость (`deception`)

По Anderson et al. 2018: **Dec = 1 − P(G1) / P(ref)**, где P(ref) = P(S), если планировщик включён и P(S) определена, иначе P(O). `greedyTrap` берётся из `outcomes[].trap` (с учётом `aliases`); неразрешённый бюджетом исход даёт `null`, а не ловушку. `null` при P(ref) = 0. Отрицательное значение — жадный агент за 12 ходов побеждает чаще, чем S находит победу за `depth` ходов (разные горизонты). **`greedyTrap`** — первый ход G1 (максимум немедленной силы) по оракулу seed 0 не ведёт к победе в пределах горизонта; `greedyTrapSeedShare` — то же по всем seed.

## E. Чувствительность к seed (`seedSensitivity`)

`minTurns[]`, `bestHp[]` по seed; `minTurnsSpread`, `bestHpSpread` — max − min по найденным значениям; `winnableShare` = P(O) по тому же правилу разрешённости (`null`, если ни один seed не разрешён), `unresolvedSeeds` — число неразрешённых.

## Хрупкие клетки (`fragileCells`, `--fragile`)

Каждая стартовая цветная сущность перекрашивается в каждый другой цвет палитры (веса > 0 и цвета поля). Перекраска делается только в копии снимка, не в данных уровня. Для каждого варианта считается P(G1) по seed; выводятся клетки с |ΔP(G1)| > 0,2. `minTurns` при перекраске не пересчитывается (слишком дорого) — упрощение.

## Ограничения

- Горизонт по умолчанию 3 хода; бой, требующий больше, будет `winnable: false` (например, арена Тролля рассчитана на 6 ходов). С дверью (02.10.2026) выход добавляет к ходам до целей 0–2 хода (класс расстояния двери), поэтому бой с целями на 2–3 ходу и дальней дверью может выйти за горизонт: смотрите `minGoalTurns` и агентов.
- Луч и бюджет делают `firstMoveWinShare` нижней оценкой, а `trapShare` — оценкой «среди исследованного».
- Порядок и дедупликация цепей — те, что в `availableMoves`: он объединяет пути с одинаковой конечной клеткой, набором немелких целей, числом врагов (до 7) и остатком силы, поэтому редкие разные исходы могут склеиться.
- Предметы усечены (`itemBeam`), жадный агент их не использует.
- Честный планировщик скрывает только первое пополнение и сравнивает ограниченное число кандидатов.
- `--json` анализирует уровень как авторский бой редактора. Определение боя карты, сохранённое в JSON, теряет его метаданные (отмеченные цели, пассивность неотмеченных врагов, разрешения инструментов), поэтому бои карты анализируйте через `--node`.
- Метрики не оценивают читаемость, обучаемость и эмоцию боя; их проверяет плейтест.
